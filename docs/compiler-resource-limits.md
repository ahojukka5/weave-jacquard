# Compiler resource limits

Jacquard bounds every byte stream and generated text file it accepts from the
trusted external `weavec` process. Compiler correctness remains `weavec`
authority; resource admission is Jacquard responsibility.

## Current ceilings

The canonical constants live in `weave_frontend.compiler.limits`:

| Limit | Value | Applies to |
|---|---:|---|
| `MAX_COMPILER_OUTPUT_BYTES` | 4 MiB | combined compiler stdout and stderr |
| `MAX_COMPILER_PROTOCOL_BYTES` | 16 MiB | each manifest or diagnostics JSON file |
| `MAX_WIR_BYTES` | 64 MiB | one frontend-validation WIR file |

The stdout and stderr limit is combined. A compiler cannot consume the full
allowance independently on both streams.

## Bounded process execution

Committed builds, frontend validation, and production virtual-candidate builds
use one selector-based process runner:

```text
start compiler in a new process group
→ drain stdout and stderr concurrently
→ stop at wall-clock deadline or combined byte ceiling
→ kill the complete process group
→ retain only the bounded prefix and termination evidence
```

The result distinguishes:

- normal process exit;
- `timed_out = true`;
- `output_limited = true`.

When Jacquard terminates the compiler, the public and retained compiler return
code is `null`. A signal generated by Jacquard's kill is not presented as the
compiler's semantic exit status.

An output-limited or timed-out run can never become a successful build even if
the compiler wrote an apparently valid manifest, diagnostics document, or
executable before termination. Failed builds remove the executable.

## Protocol file admission

Compiler manifest and diagnostics files are read as bytes with a one-byte
lookahead. A file over `MAX_COMPILER_PROTOCOL_BYTES` is rejected before UTF-8 or
JSON decoding.

This protects against:

- an inaccurate `stat` result followed by file growth;
- whole-file `read_text()` allocation;
- oversized but syntactically valid JSON;
- oversized malformed JSON.

Committed and virtual-candidate build paths delete oversized raw compiler
protocol files before artifact hashing and publication. The bounded Jacquard
`diagnostics.json` retains the refusal reason instead. Small malformed protocol
files may still be retained as forensic evidence under their verified hashes.

## WIR admission

`WeavecValidator` reads generated WIR through the same bounded byte-first helper.
A successful compiler exit without WIR is invalid. A WIR larger than
`MAX_WIR_BYTES`, invalid UTF-8, or an I/O failure produces:

```text
valid = false
wir = null
```

with explicit diagnostic and limit fields. The oversized WIR is confined to the
private temporary validation directory and is deleted when that directory
closes.

## Retained evidence

Committed build manifests and diagnostics record:

- `compiler_output_limit_bytes`;
- `timed_out`;
- `output_limited`;
- the compiler protocol-file ceiling in `diagnostics.json`.

Production virtual-candidate manifests record the same output fields. Candidate
verification recomputes the content-derived build key with the recorded output
ceiling and requires successful builds to show both termination flags false.
Candidate manifest reads are also bounded.

## Cache identity

The effective compiler output ceiling is part of committed and virtual-candidate
build input identity. A successful build produced under a more permissive limit
cannot satisfy a later request under a stricter limit.

The output limit affects evidence policy even when compiler source, binary,
target, and executable bytes would otherwise be identical.

## Compatibility boundary

`BoundedProcessResult` supports the historical internal four-value unpacking
shape:

```text
returncode, timed_out, stdout, stderr
```

New production paths read `output_limited` explicitly. This compatibility exists
to avoid duplicating the established candidate verifier; it is not a public
subprocess API.

## Distinction from behavioral sandboxing

The compiler is a configured trusted tool and does not run inside the user
program Bubblewrap sandbox. Compiler process limits prevent runaway output and
wall-clock consumption; they do not claim filesystem, network, syscall, memory,
or process-count isolation.

Native executables produced by the compiler are run only through the separately
reported strict behavioral sandbox policy.

## Remaining operational limits

This work does not yet impose:

- compiler address-space or CPU-time rlimits;
- aggregate build-root or candidate-root quotas;
- database size limits;
- artifact retention or garbage collection;
- per-project compiler concurrency quotas.

Those require explicit operator policy and evidence rather than silent deletion
or inferred safety.
